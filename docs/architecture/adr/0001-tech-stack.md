# ADR-0001：技术栈选型 —— Phaser 3 + Vite 5 + TypeScript，逻辑分辨率固定 960×640

- **状态**：Accepted（MVP 立项时确定，未变更）
- **日期**：MVP 立项
- **相关**：ADR-0002（零外部素材）、ADR-0004（性能红线）

---

## Context

《知识割草王》是「答题 + 无双割草」的闭环小游戏，MVP 需要同时满足四个约束：

1. **交付快**：核心闭环（答题 → 割草 → 结算 → 再来一次）要在很短时间内跑通，没有时间自研引擎或渲染层。
2. **到处能跑**：目标用户是 9–18 岁，设备混杂（低配 Windows 台式机、家长手机、学校平板），必须靠浏览器直接打开，不能要求安装。
3. **处理量级**：同屏要稳定容纳数十个移动小怪 + 弹丸 + 特效，且**帧率不能掉**（割草手感的底线）。
4. **可交接**：项目会经手多人（工程、美术、调参），数值要能被非程序员改，代码要能被下一个人读懂。

可选的路线大致三条：

| 路线 | 优点 | 致命问题 |
| --- | --- | --- |
| 原生 Canvas 2D 自研 | 无依赖、包体最小、性能完全可控 | 精灵/补间/输入/缩放/音效全部自己写，MVP 时间内写不完 |
| **Phaser 3** | 精灵/补间/输入/缩放/相机/场景生命周期开箱即用；社区成熟；2D 渲染性能足够 | 引入约 1.5 MB 依赖 |
| Unity / Cocos 等重型引擎 | 工具链完整 | 需要打包/安装/导出，违背「浏览器直接打开」；构建与协作成本高 |

同时需要一个构建工具与类型系统：Vite 提供零配置的开发服务器与生产构建；TypeScript 让「配置结构 → 解析结果」这条链（ADR-0003）具备编译期保障。

**分辨率是这条决策里最容易出错、也最需要写下来的一环。** 立项时团队里流传的口径是 1280×720（常见横屏尺寸），但实际落地的配置写的是 **960×640**。这个不一致在 T-010 阶段由 team-lead 做无头浏览器验证时暴露：他按 1280×720 推算的布局坐标与截图对不上，回头查代码才发现基准是 960×640，导致一轮布局计算全部作废。

---

## Decision

1. **引擎**：Phaser 3（`phaser: ^3.80.1`），渲染模式 `Phaser.AUTO`（优先 WebGL，降级 Canvas）。
2. **构建**：Vite 5（`vite: ^5.4.8`）；`npm run build` = `tsc --noEmit && vite build`，**类型检查先于打包**，类型不过不产出制品。
3. **语言**：TypeScript 5（`typescript: ^5.5.4`）。
4. **逻辑分辨率固定 960×640**（3:2），通过 `Phaser.Scale.FIT` + `CENTER_BOTH` 自适应任意窗口与手机屏幕。**不是 1280×720。**
5. 关闭 Phaser 启动 banner（`banner: false`），保持界面干净。

---

## Rationale

**为什么是 Phaser 3：**

- 它恰好覆盖了我们「不想自己写」的那一层：场景生命周期、补间动画、指针/键盘输入、缩放管理、相机震动、对象分组与深度。这些自研都要花掉 MVP 大半时间，且质量不如成熟实现。
- `Phaser.AUTO` 让 WebGL 不可用时自动降级，兼容学校机房的低配机器。
- 它的 Sprite / Image / Graphics 抽象与 ADR-0002（程序化生成贴图）配合良好：`Graphics` 画完直接 `generateTexture()` 变成可复用的贴图 key。

**为什么固定 960×640 而不是 1280×720：**

- **判定公平性**：答题公平是产品的立身之本。`Scale.FIT` 保证所有设备看到的是同一个等比缩放后的画面，判定区与选项尺寸的相对关系在任何屏幕上完全一致。逻辑分辨率本身取多少并不影响这一点，但取小一点有实打实的好处。
- **性能**：逻辑分辨率越小，同屏需要绘制与填充的像素越少。割草场景同屏数十个单位 + 特效，960×640 比 1280×720 少约 44% 的像素填充量，这对低端设备是实打实的帧率。
- **3:2 更接近手机横屏比例**：960×640 = 3:2，1280×720 = 16:9。手机横屏通常是 20:9 甚至更长，16:9 反而留白更多；3:2 在竖屏平板与横屏手机上的黑边分布更均衡。

**为什么没有选更轻的方案：** 评估过直接用 Canvas 2D 自研，放弃的原因是补间（武器栏切换动画、击杀扩散环、飘字）和输入管理（键盘 + 指针热区 + 多键组合）的自研成本远超收益，且容易在边界情况上出 bug。MVP 阶段买成熟方案是划算的。

---

## Tradeoffs & Costs

1. **包体约 1.59 MB（gzip 372 KB）**，其中绝大部分是 Phaser 本体。对一个小游戏而言偏大，首屏需要一次完整下载。
   - 缓解：MVP 阶段接受，后续优先级为「开启 brotli/gzip → Phaser custom build 裁剪不用模块 → 拆包」。
2. **逻辑分辨率取小意味着 UI 可用面积紧张**。960×640 下，底部武器栏（`SLOT_H = 56`）+ 顶部 HUD（约 64px）吃掉近 120px 垂直空间，战斗区只剩约 520px。T-010 中 HUD 文本与武器栏一度只差 2px 就重叠（见 `Hud.ts:87` 的注释），就是面积紧张的直接影响。
   - 连带后果：武器栏热区向下外扩的 32px 里只有 10px 落在可视区内（详见 `ARCHITECTURE.md` 第 6.4 节）——**扩展热区这件事在这个分辨率下收益有限，正确解法是整体上移而不是继续外扩。**
3. **固定 3:2 会在极端宽高比设备上产生黑边**。这是 `Scale.FIT` 的必然结果，接受。
4. **`Phaser.AUTO` 的降级路径没有专门验证过**。WebGL 可用时的表现是验证过的，Canvas 降级路径只在理论上成立。若目标设备里有明确不支持 WebGL 的机器，需要补一轮 Canvas 模式的帧率验证。
5. **Phaser 版本锁在 3.80.x**。Phaser 4 的 API 有 breaking change，升级需要评估场景与输入相关代码。

**给后续维护者的两条警告（都是踩过的坑）：**

1. **⚠️ 逻辑分辨率是 960×640，不是 1280×720。** 任何人做布局计算、写死坐标、或在验证脚本里推算屏幕位置时，请直接读 `src/main.ts:16-17` 的常量，不要凭印象。T-010 阶段已经因为按 1280×720 推算而白算过一整轮布局。需要动态取尺寸时用 `this.scale.width / this.scale.height`，不要在业务代码里写死 960/640。
2. **⚠️ `main.ts:38` 曾为无头验证临时挂过 `(window as any).__game__` 调试句柄，已还原为 `new Phaser.Game(config);`**。如果你在旧脚本里看到 `window.__game__`，那是历史脚本，当前代码里没有这个句柄。现有的只读调试句柄是 `window.__KB_DEBUG__`，位于 `GrassCuttingScene.ts:272-286`，出厂前应移除。
